Security bolted on at the end is a patch job, not a system

The common pattern: build the product, ship it, then run a security audit and fix whatever it finds. That works, in the sense that the holes get patched — but every fix is now a change to a system already in production, touching code that was never designed with that constraint in mind. Security by design is the alternative: treating security as a requirement from the first architecture decision, not a review step at the end.

What it actually means in practice

Least privilege by default

Every part of a system — a user role, a service, an API key — gets access to only what it specifically needs, not broad access that happens to be convenient. Narrowing this down later, after other parts of the system have come to depend on that broad access, is far harder than starting narrow.

Data minimization

Collecting and storing only the data a feature actually requires, rather than everything that might be useful someday. Data you never collected can't be the subject of a breach.

Secure defaults, not secure options

The safe configuration should be what happens automatically, not a setting someone has to remember to turn on. A login flow that requires strong passwords by default is secure by design; one where strong passwords are merely "recommended" is not.

Threat modeling before the build, not after

Asking "what could go wrong here, and who would want to make it go wrong" as part of designing a feature — not as a separate audit conducted once the feature already exists.

Why retrofitting it costs more

Three reasons this isn't just caution talking:

  • Architecture is expensive to change after the fact. A data model built without access boundaries in mind often needs real restructuring to add them properly later, not just a permissions check bolted on top.
  • Fixes made under pressure are riskier. A security gap found in production usually needs fixing fast, which is exactly the condition under which new bugs get introduced.
  • Some gaps can't be fully closed after the fact. If sensitive data was logged, cached, or sent to a third-party service before anyone caught it, no later fix removes it from everywhere it already went.

What this looks like on a real project

In practice, security by design isn't a separate phase with its own line item — it's a set of questions asked at each stage of a build already happening: what does this role actually need access to, what happens if this input is malicious, what's logged and for how long, what happens if this third-party integration is compromised. None of it requires a dedicated security team for most business software; it requires asking those questions while the architecture is still easy to change.
